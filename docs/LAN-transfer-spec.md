# ADBType 局域网传输协议 & 界面规格

本文档是 macOS 端（SwiftUI，`macos/Sources/LANTransfer.swift`）、Windows 端（Avalonia + .NET 8，`windows/`）以及规划中的移动端（`mobile/`）之间的**兼容契约**。
两端必须严格按本文实现，才能互相发现、配对、收发。

---

## 1. 总体

- 纯局域网直连，无服务器、无账号、无加密（明文 TCP）。
- 发现：UDP 广播，固定端口 **52730**。
- 传输：TCP，端口在广播报文中通告（随机端口，通常由系统分配）。
- 所有 JSON 均为 UTF-8 编码，字段名为 camelCase。
- 一次「发送动作」（一段文字，或一批文件中的一个文件）新建一条 TCP 连接，完成后发送 `bye` 并关闭。

---

## 2. 设备发现（UDP）

### 2.1 广播

每台设备启动后每 **2 秒**向以下地址发送一次 UDP 广播报文：

- `255.255.255.255:52730`
- `127.0.0.1:52730`（本机回环，方便同一台电脑跑两个实例联调）

报文（UTF-8 JSON，无 BOM）：

```json
{"app":"ADBTypeLink","v":1,"id":"<稳定的设备唯一 ID>","name":"<设备名>","port":<TCP 监听端口>}
```

- `app` 固定 `"ADBTypeLink"`，用于过滤其它程序的广播。
- `v` 协议版本，当前 `1`。
- `id`：设备唯一 ID。macOS 端首次启动生成 UUID 并持久化（UserDefaults key `lanDeviceID`），之后不变；Windows 端同样要持久化（见 §8）。
- `name`：展示名，macOS 用 `Host.current().localizedName`（如「pichs 的 MacBook Pro」）。
- `port`：TCP 监听端口（1–65535）。

### 2.2 接收

- 监听 `0.0.0.0:52730`（UDP）。
- **允许同一端口被多个进程同时绑定**（macOS 用 `SO_REUSEADDR + SO_REUSEPORT`；Windows 用 `SO_REUSEADDR` + 关闭独占模式），这样同一台机器开多个实例都能收到广播。
- 收到报文后：
  - 校验 `app == "ADBTypeLink"`、`id` 非空且 **不等于本机 id**、`name` 非空、`port` 在 1–65535，否则**静默丢弃**。
  - 以报文的**来源 IP**（不是 payload 里的字段）+ `port` 生成/更新 peer 记录；同一 `id` 只保留一条，每次收到刷新 `lastSeen`。
  - `v` 不等于 1 时仍接受（向前兼容），仅记录日志。
- 超过 **8 秒**没收到某设备广播，则从「附近设备」列表移除（每 3 秒清理一次）。
- 设备按名称排序；新设备出现、选中项消失时更新界面。

> 同机多实例兜底：多个进程绑定同一 UDP 端口时，发往 `127.0.0.1` 的单播只会投递给其中
> 一个 socket。为了让同一台电脑上的两个实例也能双向发现，Windows 端额外在
> `%TEMP%\\ADBTypeLink\\instances` 写心跳文件（2 秒刷新、8 秒过期）。
> 这是本机内部的补充机制，**不改变任何网络报文**，跨设备仍完全走 UDP 广播，不影响互通。

## 3. TCP 帧格式

每条 JSON 消息：

```
+----------------+--------------------------------+
| 4 字节大端长度  |  JSON 正文（UTF-8，长度字节数）   |
+----------------+--------------------------------+
```

- 长度上限 **16 MiB**（16777216）。超出视为协议错误，断开连接。
- 文件内容**不套 JSON 帧**：先发一条 `file` 头，随后直接写 `size` 个原始字节。
- 读长度 / 读正文都必须循环读满，不能假设一次 recv 到位。

## 4. 连接与握手

### 4.1 时序

```
发送方 client                                  接收方 server
    |  TCP connect(peer.host, peer.port) 超时 6s   |
    | ----------> hello {app,v,id,name,code?} ---> |
    |                                             | 校验 / 配对判断
    | <---- hello_ok {name,id} 或 pair_required ---|
    |       或 error {message}                    |
    |                                             |
    | ----------> text {text} / file {name,size} ->|
    |                                             |
    | <--------------------------- ok ------------|
    | ----------> bye --------------------------->|
    |  close                                      |
```

### 4.2 hello（client → server）

```json
{"app":"ADBTypeLink","v":1,"id":"<发送方设备 id>","name":"<发送方设备名>","code":"123456"}
```

- `code` **仅在用户在配对弹窗里输入了配对码时携带**；已配对后的普通发送不带。
- 发送方在收到 `hello_ok` 后把对方 id 记入已配对集合（本机的 paired 集合）。

### 4.3 接收方处理 hello

1. 必须是合法 JSON 对象且 `app == "ADBTypeLink"`、`id` 非空且 ≠ 本机 id、`name` 非空；否则回
   `{"type":"error","message":"协议不匹配，请升级两端应用"}`（能回就回）然后关闭。
2. 若该 `id` **已在已配对集合**：直接 `{"type":"hello_ok","name":<本机名>,"id":<本机 id>}`。
3. 若未配对：
   - 从 hello 取 `code`；`code` 去掉空白后**必须与本机当前 6 位配对码完全相等**。
   - 不相等（含缺失）：记下「对方正在请求配对」（界面提示），回复
     `{"type":"pair_required","name":<本机名>}`，关闭连接。
   - 相等：把对方 id 记入已配对集合并持久化，回复 `hello_ok`（带 `name`、`id`）。

### 4.4 发送方处理握手响应

读取一帧 JSON：

| 响应 | 处理 |
| --- | --- |
| `hello_ok` | 握手成功，把对方 id 记入本机已配对集合；继续发送正文 |
| `pair_required` | 首次连接，界面弹出配对框（提示「配对码不对」由 UI 判断） |
| `error` | 显示 `message`，失败 |
| 超时 / 连接失败 / 无法解析 | 「连不上 <对方名>，请确认两台设备在同一局域网、对方应用已打开」或「对方没有响应」 |

配对提示文案（保持与 macOS 一致）：

- 首次发送：`首次给「<name>」发送，需要输入对方屏幕上显示的 6 位配对码`
- 握手无响应：`对方没有响应`
- 版本/协议不对：`协议不匹配，请确认两端版本一致`
- 配对码错误（主动配对的 UI 文案）：`配对码不对，再看一眼对方屏幕上显示的数字`

## 5. 消息类型

| type | 方向 | 字段 | 说明 |
| --- | --- | --- | --- |
| `hello` | C→S | app, v, id, name, code? | 见 §4 |
| `hello_ok` | S→C | name, id | 握手成功 |
| `pair_required` | S→C | name | 需要配对码 |
| `error` | 双向 | message | 出错，读完即关 |
| `text` | C→S | text | 一段文字（可含中文/emoji） |
| `file` | C→S | name, size | 后跟 size 字节原始数据 |
| `ok` | S→C | — | 已收到并处理完一条 text / file |
| `bye` | C→S | — | 本次发送结束，接收方结束循环并关闭 |

- 发送空文字：客户端直接拒绝，提示「先输入要发送的文字」，**不建连接**。
- 文件 size：发送方要求 > 0，否则「读不到文件：<name>」；接收方接受 size ≥ 0（0 字节文件也合法）。
- 一条连接里接收方可循环处理多条内容消息（text / file / bye），保持兼容；发送方每次连接只发一条内容。
- 未知 type / 无法解析：接收方直接关闭连接；发送方显示「发送文字失败，对方没有确认」/「对方没有确认收到文件」。

## 6. 文件传输

1. 发送方发 `{"type":"file","name":"<原始文件名>","size":<字节数>}`。
2. 立即写 `size` 个原始字节（分块，256 KiB 一块即可），**不插入任何帧头/分隔符**。
3. 接收方校验：
   - `name` 只取路径最后一段（去掉 `/`、`\\` 等目录部分），拒绝空名、`.`、`..`。
   - 保存到「接收目录」，重名时依次尝试 `<base> (2).<ext>`、`<base> (3).<ext>`……
   - 接收中断/磁盘错误：删除半截文件，回 `{"type":"error","message":"保存文件失败"}` 并关闭。
4. 接收方回 `{"type":"ok"}`；发送方收到后发 `bye` 并关闭。
5. 多文件：发送方按文件逐个新建 TCP 连接（每文件一次握手），界面显示「3/5 文件名」与总进度。

---

## 7. 超时与错误

- TCP connect 超时：**6 秒**。
- 已建立连接上的读写超时：**30 秒**。
- 单帧 JSON 上限 16 MiB。
- 任何异常都只影响本次连接，服务保持监听。
- 应用需要处理：对方中途退出、Wi-Fi 断开、防火墙拦截、端口占用（52730 被占用时提示「端口 52730 被占用，无法启动局域网发现」）。

## 8. 本机状态持久化

| 数据 | macOS | Windows |
| --- | --- | --- |
| 设备 ID | UserDefaults `lanDeviceID` | `%APPDATA%\\ADBTypeLink\\device.json`（或等价的 settings 文件） |
| 已配对设备 ID 列表 | `~/Library/Application Support/ADBType/paired.json`，JSON 字符串数组，如 `["id1","id2"]` | `%APPDATA%\\ADBTypeLink\\paired.json`，同格式 |
| 聊天记录 | `~/Library/Application Support/ADBType/chat.json` | `%APPDATA%\\ADBTypeLink\\chat.json` |
| 接收目录 | UserDefaults `lanReceiveDir` | 设置文件；默认 `%USERPROFILE%\\Downloads\\ADBType 接收` |

- Windows 端**不要**读写 macOS 的 `ADBType` 目录（在 macOS 上本地调试时请用 `~/Library/Application Support/ADBTypeLink/`，避免与正式 macOS 端数据冲突）。
- 聊天记录是**单线程**（所有设备共用一条时间线，类似微信「文件传输助手」），元素字段：
  `id`(uuid)、`direction`(`incoming`/`outgoing`)、`peerName`、`date`、`kind`(`text`/`file`)、`text`、`fileName`、`filePath`、`fileSize`。
- 最多保留 500 条；清空聊天记录**不删除**已收到的文件。

## 9. 界面规格（两端一致）

目标：像微信/文件传输助手一样的聊天窗口——**左边是设备列表，右边是聊天记录，输入框固定在底部**。

### 9.1 窗口结构

```
+----------------------+---------------------------------------------+
| 侧栏 260px            | 聊天头部（对方名 / 在线 / 已配对 / 配对按钮）    |
|  ADBType 传输         +---------------------------------------------+
|  搜索状态              |                                             |
|  ── 附近设备 ──        |  消息列表（可滚动，占满剩余高度）                |
|   [设备行]            |   左：对方头像 + 名字 + 时间 + 气泡             |
|   [设备行]            |   右：我 → 对方 + 时间 + 气泡                  |
|  ...                 |                                             |
|  ── 本机 ──           |                                             |
|   设备名 / 配对码       +---------------------------------------------+
|   接收目录 / 已配对数量  | 待发送文件 chips（如有）                       |
|  状态文字              | [📎] [输入框.................] [发送]        |
|                      | 提示：Enter 发送 · 可拖拽文件                  |
+----------------------+---------------------------------------------+
```

- 窗口最小尺寸：macOS 720×640；Windows 900×620。聊天区随窗口拉伸。
- 侧栏可滚动；设备行显示图标、名称、`已配对`/`未配对` 徽标、`在线`、未配对时「配对…」按钮。
- 本机块：设备名、6 位配对码（大号等宽字体、可复制、可「换一个」）、接收目录（点击打开、可修改）、已配对 N 台 + 清除配对。
- 聊天头部：对方名称，在线状态，未配对时「配对」按钮；`⋯` 菜单：清空记录、修改接收目录、在文件管理器中打开接收目录。
- 消息气泡：
  - 文字：自动换行、可选中，右键「复制文字」。
  - 文件卡片：文件名、大小、状态（已发送/已保存），按钮 发送方「打开」/接收方「显示」（在文件管理器中定位）。
  - 空状态文案：`还没有消息`、`收到的文字和文件会像聊天一样显示在这里，发出去的内容也会留在上面`。
  - 新消息自动滚到底部。
- 输入区固定底部：
  - 附件按钮：选择文件（多选），文件进入**待发送列表**（chips），可单个移除、可清空；
  - 文字输入框：Enter 发送，Shift+Enter 换行（macOS 用普通输入框即可，Cmd+Enter 发送）；
  - 「发送」按钮：发送文字；待发送文件有单独的「发送文件」按钮；
  - 拖拽文件到聊天区/窗口任意位置 → 加入待发送列表（高亮提示）；
  - 未选择设备时输入框禁用，提示「先在左侧选择设备」。
- 配对弹窗：标题「与「<name>」配对」，6 位数字输入（自动过滤非数字、自动聚焦）、「粘贴」、错误提示、「取消」/「配对并发送」；配对成功后自动重发刚才的内容。
- 状态提示：保持在侧栏底部或聊天头部下方，成功绿色、失败红色、普通灰色；文案与 macOS 现有文案一致。
- 首次运行提示：Windows 需在「Windows 安全中心 → 防火墙」允许专用网络；macOS 需允许「本地网络」权限。

### 9.2 交互细节

- 选中设备后，输入区上方显示「发给 <name>」；未配对时附加「首次发送需输入对方配对码」。
- 发送中：显示进度条（多文件时显示总进度）与「正在发送 <文件名>…」；发送期间禁止重复发送。
- 收到配对请求（对方在等你给码）：侧栏/聊天区显示「「<name>」正在请求配对，把本机配对码告诉对方」。
- 清空记录需二次确认；文案说明不会删除已收到文件。

## 10. 验收清单

- [ ] 两端同时启动，10 秒内互相出现在「附近设备」。
- [ ] 首台设备向另一台发送文字：弹配对框，输入对方配对码后发送成功，双方聊天记录各出现一条。
- [ ] 配对码输错：提示错误，可重试。
- [ ] 已配对后再次发送：不再弹配对框。
- [ ] 发送 1 个文件、一次发送多个文件：进度正常，接收目录出现文件，重名自动加序号。
- [ ] 接收方收到文字/文件后立即出现在聊天记录并自动滚动到底部。
- [ ] 重启两端：设备 ID、配对关系、聊天记录、接收目录都恢复。
- [ ] 同一台电脑开两个实例：能互相发现（靠 127.0.0.1 广播）。
- [ ] 对方退出后发送：3 秒内提示连接失败，不崩溃。
- [ ] 中文/emoji 文字、超长文件名、0 字节文件（接收侧）均正常。
